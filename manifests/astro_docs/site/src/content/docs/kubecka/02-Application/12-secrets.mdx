I `Secrets` memorizzano dati sensibili come password, token e chiavi. Sono codificati
in base64 e salvati all'interno di ETCD.

<Aside type="caution">
`base64` è una tecnica di `Encoding`: chi ha accesso al cluster puo` decodificare facilmente i valori.
</Aside>

### *Tipi comuni*

<CardGrid>
  <Card title="Opaque" icon="document">
    Coppie chiave-valore generiche, come password o API key.
  </Card>

  <Card title="dockerconfigjson" icon="node">
    Credenziali per registry Docker privati.
  </Card>

  <Card title="TLS" icon="setting">
    Certificati pubblici e chiavi private TLS/SSL.
  </Card>
</CardGrid>

### *Come vengono usati dai Pod*

<Steps>
1. Il `Secret` viene definito nel cluster.
2. Il Pod lo referenzia nel manifesto.
3. Kubernetes lo espone come variabile d'ambiente oppure come volume.
4. Il container usa il valore durante l'esecuzione.
</Steps>

### *Modalita` di consumo*

| Metodo | Descrizione |
| --- | --- |
| Variabili d'ambiente | Il valore viene iniettato come env var nel container |
| Volume | Il Secret viene montato come file nel filesystem |

<Aside type="note">
Il mount come volume è spesso preferibile perchè gli aggiornamenti del `Secret` possono riflettersi nei file senza riavviare il Pod.
</Aside>

### *Best practices*

<CardGrid>
  <Card title="RBAC" icon="close">
    Limitare chi può leggere i `Secrets`.
  </Card>

  <Card title="Encryption at Rest" icon="warning">
    Protegge i `Secrets` salvati in `ETCD`.
  </Card>

  <Card title="External Vaults" icon="puzzle">
    Integrazione id strumenti come `HashiCorp Vault` o cloud secret managers.
  </Card>
</CardGrid>
