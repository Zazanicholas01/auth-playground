### *CSI Provisioner*

Il `Provisioner` osserva le `PVC` e crea lo storage richiesto.

<Steps>
1. Viene creata una `PVC`.
2. Kubernetes rileva la `StorageClass`.
3. Il `CSI Provisioner` chiama le API dello storage.
4. Viene creato il volume fisico.
5. Kubernetes crea il `PV` e lo collega alla `PVC`.
</Steps>

### *Idea chiave*

| Componente | Ruolo |
| --- | --- |
| `CSI` | Standard di integrazione storage |
| `Driver` | Plugin del vendor |
| `Provisioner` | Crea i volumi quando arriva una `PVC` |
| `StorageClass` | Definisce come creare lo storage |

<Aside type="note">
Il `Local Path Provisioner` è utile in sviluppo, ma non offre replica o alta affidabilita`.
</Aside>

| Driver | Punto di forza | Limite principale | Uso tipico |
| --- | --- | --- | --- |
| `Longhorn` | Semplice, cloud-native, con replica e backup | Meno adatto a scenari molto complessi | Cluster piccoli o medi |
| `OpenEBS` | Modulare e flessibile | Richiede piu` scelta e progettazione | Storage custom o alte performance |
| `Ceph / Rook` | Molto completo e potente | Complesso da gestire | Ambienti enterprise |
| `Local Path Provisioner` | Leggero e facilissimo | Nessuna replica o HA | Sviluppo e lab |
